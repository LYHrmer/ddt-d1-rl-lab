# 合同 08 附录 A：导出门槛失败后，资格如何评测

2026-10-16 登记，**在 8× 策略的任何资格评测之前**。本附录不改变合同 08 的任何预测、阈值、预算、训练结果，也不改冻结导出器或冻结评测器的任何一行。

## 1. 发生了什么

8× 训练完成（8,388,608 transitions / 83,886,080 native，E1 等价性 256/256 通过，输入全程未变）。按合同 §7 的顺序执行冻结导出器 `tools/export_d1_ppo.py`，它在写出元数据之前拒绝了这个策略：

```
ValueError: ONNX parity failed: Torch/ORT=1.3113021850585938e-06, SB3/Torch=1.2814998626708984e-06
```

冻结导出器有两道一致性检查：Torch 对 ORT 的门槛是 1e-5（1.31e-6，**通过**），SB3 对 Torch 的门槛是 1e-6（1.28e-6，**未通过**）。输出目录 `scale08_export_01` 只留下一个没有元数据的 `policy.onnx`，原样保留。

## 2. 零物理步诊断（回执 `scale08_export_diagnosis_01`）

| 策略 | SB3/Torch 最大差 | 超过 1e-6 的元素 | 未截断动作最大幅值 | 最大权重 | 差 / (float32 机器精度 × 幅值) |
|---|---:|---:|---:|---:|---:|
| 03d 1×（当年导出通过） | 3.58e-7 | 0 / 1024 | 1.57 | 1.39 | 1.92 |
| 8× | 1.28e-6 | 4 / 1024 | 6.79 | 3.31 | **1.58** |

float32 的舍入误差随数值大小增长。8× 策略的权重与输出幅值都更大，绝对误差因此变大；**按幅值归一化后，8× 的误差反而比当年通过的 03d 还小**。所以这不是导出出了错，而是冻结导出器的绝对容差不随输出幅值缩放。这是冻结工具的一个已查明局限，**不在本合同内修改**，记为下一次解冻冻结导出器时的待办。

## 3. 本附录的决定（事前写定）

1. **导出门槛记为 FAIL**，按冻结规则原样记录；不改门槛、不重跑导出、不手工写元数据。
2. **C++ 黄金比对不执行**：它需要导出器写出的元数据与黄金夹具。合同 08 的部署链路记为**未验证**。合同 08 从未把部署作为资格条件（§5：Python 评测器决定资格），所以这不改变资格判定的规则，但任何结果都**不得**表述为"已可部署"。
3. **资格评测照常进行，仍用冻结评测器 `tools/evaluate_d1_ppo.py`**，输入改为 `--checkpoint evidence/career_contract_08/scale08_train_01/policy.zip`。这是冻结评测器原本就支持的输入方式：它用同一个训练出处校验（`check_checkpoint`，要求 `policy.zip`、训练 COMPLETE、计划步数等于实际步数、随机初始化、无教师、训练源码未变），用 SB3 的确定性动作截断到 [−1, 1]。被评测的仍是**唯一的最终策略**，不存在挑选。
4. 资格评测参数与合同 08 相同：`--phase pilot`、三条任务、seed 7001、delay 0、`--max-native-steps 18000`，只执行一次。
5. 判定用已提交的 `tools08/verify_scale08.py`，规则不变。

## 4. 为什么这不是"事后挑选"

这个决定在任何资格结果出现之前写定并推送；它只改了"评测器读哪种格式的同一个策略"，没有改被评测的策略、评测器、阈值或预测。ONNX 与 SB3 的动作差最大 1.31e-6，远小于任何资格门槛的量级（最小的门槛是 0.02），换成 ONNX 评测也不会改变任何一个门槛判定；但这一点只是量级论证，**没有实测**，因为导出失败后不再产生可评测的 ONNX。
